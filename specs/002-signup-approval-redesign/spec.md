## Clarifications

### Session 2026-08-22

- Q: 회원가입 성공 후 사용자를 어디로 보내는가? → A: `/login`으로 리다이렉트하고, 로그인 페이지 상단에 "가입이 완료되었습니다. 관리자 승인 후 로그인할 수 있습니다."라는 배너를 표시한다. 배너는 다음 페이지 이동 시 자동으로 사라진다.
- Q: 모바일 하단 탭 바는 몇 개의 탭으로 구성되는가? → A: 3탭 — 내 문제집(`/sets`) · 공개 문제집(`/public-sets`) · 프로필(`/profile`). 프로필 탭은 아이디 표시와 로그아웃 버튼을 담고, 향후 계정 관련 기능을 여기에 확장한다.
- Q: 학습/암기 모드에서 하단 탭 바를 유지하는가? → A: 숨긴다. 학습 몰입을 위해 `/sets/[id]/study`와 `/public-sets/[id]/study` 두 경로에서만 하단 탭 바를 렌더하지 않고, 목록으로 나가면 다시 노출된다. 다른 상세·편집 화면에서는 탭 바가 유지된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원가입 승인제 (Priority: P1)

새로 가입한 사용자는 계정이 생성되지만 즉시 앱을 이용할 수는 없다. 소유자가 별도 경로(DB 값 변경 등, 앱 UI 밖)로 계정을 "승인"해야 로그인이 가능해진다. 승인 전 로그인 시도는 명확한 안내 메시지와 함께 거부된다.

**Why this priority**: 앱이 공개 URL로 배포되면 누구나 회원가입할 수 있기 때문에, 소유자가 원치 않는 사용자의 접근을 차단하는 최소 방어선이다. 데이터 프라이버시와 리소스 관리 측면에서 배포 즉시 필요한 기능이다.

**Independent Test**: 새 계정을 만들고 → 로그인 시도 → "승인 대기 중" 메시지 확인 → DB에서 승인 플래그 변경 → 다시 로그인 → 정상 진입. 이 사이클이 앱 UI만으로(+ 한 번의 수동 DB 편집으로) 완결되면 성공.

**Acceptance Scenarios**:

1. **Given** 방문자가 회원가입 폼에서 유효한 아이디·비밀번호를 제출할 때, **When** 폼을 제출하면, **Then** 계정이 "승인 대기" 상태로 생성되고, 사용자는 `/login` 페이지로 이동하며, 로그인 페이지 상단에 "가입이 완료되었습니다. 관리자 승인 후 로그인할 수 있습니다." 배너가 표시된다. 자동 로그인은 일어나지 않는다. 배너는 다음 페이지 이동 시 자동으로 사라진다.
2. **Given** 승인 대기 상태 계정으로 로그인할 때, **When** 올바른 자격 증명을 입력하면, **Then** 시스템은 로그인을 허용하지 않고 "아직 승인되지 않은 계정입니다. 관리자에게 문의해 주세요." 같은 안내를 표시한다. 세션도 발급되지 않는다.
3. **Given** 소유자가 승인 대기 계정에 대해 DB에서 승인 상태를 활성으로 바꾼 뒤, **When** 그 계정으로 다시 로그인하면, **Then** 정상적으로 로그인되어 홈으로 이동한다.
4. **Given** 이미 승인·로그인된 사용자의 활성 세션이 있는 상태에서, **When** 소유자가 그 계정의 승인 상태를 해제하면, **Then** 다음번 서버 상호작용부터 그 사용자의 보호된 화면 접근이 거부된다.
5. **Given** 회원가입 흐름이 실패(중복 아이디 등)했을 때, **When** 오류가 반환되면, **Then** 어떤 계정도 "승인 대기" 상태로 생성되지 않는다.
6. **Given** 승인 대기 계정으로 잘못된 비밀번호로 로그인을 시도할 때, **When** 폼을 제출하면, **Then** 시스템은 자격 증명 오류를 우선 표시한다 (승인 상태 유출을 피하기 위한 보수적 우선순위).

### User Story 2 - 배민 디자인 시스템 기반 UI 전면 재설계 (Priority: P1)

기존의 임시 UI(단순 form + list)를 폐기하고, [DESIGN.md](../../DESIGN.md)의 배달의민족 디자인 시스템 토큰과 컴포넌트 어휘를 기반으로 앱 전 화면을 다시 만든다. 하나의 반응형 웹앱이 모바일 브라우저와 데스크톱 브라우저 양쪽에서 자연스럽게 동작해야 한다. 모바일 뷰에서는 배민식 하단 탭 내비게이션을, 데스크톱 뷰에서는 상단 내비게이션을 사용한다.

**Why this priority**: 앱이 실사용 대상이 되려면(설사 1인 사용자여도) 학습 몰입도와 손맛을 결정하는 시각·인터랙션 수준이 근본적으로 재작성되어야 한다. 승인제(US1)와 함께 첫 공개판의 UX 인상을 결정하는 핵심 축이다.

**Independent Test**: 모바일 뷰포트(예: 375×667)와 데스크톱 뷰포트(예: 1440×900) 각각에서 앱의 모든 기존 화면(회원가입·로그인·문제집 목록·문제집 상세·문제 생성/편집·학습/암기 모드·공개 문제집 목록/상세)을 열어 (a) 색·타이포·간격이 DESIGN.md의 토큰과 일치, (b) footer가 없음, (c) 모바일에서는 하단 탭 바가 노출되고 데스크톱에서는 상단 내비게이션이 노출됨을 확인.

**Acceptance Scenarios**:

1. **Given** 모바일 뷰포트에서 로그인된 사용자가 아무 화면에 있을 때, **When** 화면 하단을 보면, **Then** 배민식 하단 탭 바가 노출되고 정확히 3개의 탭(내 문제집 · 공개 문제집 · 프로필)으로 한 번에 이동할 수 있다.
2. **Given** 데스크톱 뷰포트에서 로그인된 사용자가 아무 화면에 있을 때, **When** 화면 상단을 보면, **Then** 상단 내비게이션 바가 노출되고 하단 탭 바는 노출되지 않는다.
2a. **Given** 모바일 뷰포트에서 학습·암기 모드 화면(`/sets/[id]/study` 또는 `/public-sets/[id]/study`)에 있을 때, **When** 화면 하단을 보면, **Then** 하단 탭 바는 노출되지 않는다. 사용자가 목록·상세 화면으로 돌아가면 다시 노출된다.
3. **Given** 어떤 뷰포트에서든 어떤 화면에 있을 때, **When** 화면을 스크롤하면, **Then** footer 영역은 어디에도 렌더되지 않는다.
4. **Given** 사용자가 문제집 상세 화면에서 학습 모드로 진입할 때, **When** 문제 카드를 보면, **Then** 카드의 라운드·그림자·간격·타이포가 DESIGN.md의 카드 컴포넌트 토큰과 일치한다.
5. **Given** 사용자가 회원가입/로그인 폼을 볼 때, **When** 입력 필드와 버튼을 보면, **Then** 입력 필드는 DESIGN.md의 `text-field` 사양(높이 48px, 12px radius, 서브틀 배경, 포커스 시 검정 보더)을 따르고, 주요 버튼은 알약 형태(`{rounded.pill}`)로 렌더된다.
6. **Given** 사용자가 문제 편집 화면에서 키워드를 입력할 때, **When** 콤마 또는 엔터로 키워드가 확정되면, **Then** 각 키워드는 DESIGN.md의 tag/chip 어휘(알약 배경 + 텍스트 + ✕)로 표시된다.
7. **Given** 사용자가 어떤 화면에서든 액션(버튼 탭 등)을 취할 때, **When** 인터랙션 피드백이 발생하면, **Then** 애니메이션은 짧고 절제된 톤(≤ 200ms, 통통 튀는 spring 아님)을 유지한다.

### Edge Cases

- **승인 상태 필드가 누락된 기존 계정**: 이미 존재하는(이전 스펙에서 만들어진) 사용자 계정은 마이그레이션 시점에 명확한 기본값(승인/미승인)을 갖도록 처리한다. 소유자 본인의 계정은 승인 상태로 시작해야 앱을 계속 사용할 수 있다.
- **승인되지 않은 사용자가 보호된 URL을 직접 입력**: `/sets/...` 등에 직접 접근하려 하면 로그인 화면 또는 "승인 대기" 화면으로 이동되고, 데이터는 어떤 것도 노출되지 않는다.
- **모바일 상단 노치·홈 인디케이터**: 하단 탭 바는 safe-area 여백을 확보해 홈 인디케이터와 겹치지 않는다.
- **매우 좁은 화면(예: 320px)**: 하단 탭 라벨이 잘려도 아이콘만으로 식별 가능해야 한다.
- **매우 넓은 화면(예: 1920px 이상)**: 콘텐츠 폭에 상한(max-width)을 두어 텍스트가 지나치게 길게 흐르지 않는다.
- **한글 폰트 로딩 실패**: DESIGN.md의 디스플레이 폰트(BM 한나체 등) 로딩이 실패해도 시스템 한글 sans-serif로 fallback되어 텍스트는 항상 읽을 수 있다.
- **다크 모드 사용자**: 이 스펙 범위에서는 라이트 모드만 지원한다 (배민 디자인 시스템의 기준 모드).

## Requirements *(mandatory)*

### Functional Requirements

**회원가입 승인제 (US1)**

- **FR-101**: 시스템은 각 사용자 계정에 대해 "승인 여부"를 나타내는 명시적 상태를 저장해야 한다. 상태는 최소 두 값("승인됨" / "승인 대기")으로 구분되어야 한다.
- **FR-102**: 회원가입은 계정을 "승인 대기" 상태로 생성해야 한다. 회원가입 성공만으로 세션이 발급되어서는 안 된다.
- **FR-103**: 회원가입이 성공하면 시스템은 사용자를 `/login` 페이지로 리다이렉트해야 하며, 로그인 페이지 상단에 "가입이 완료되었습니다. 관리자 승인 후 로그인할 수 있습니다."라는 배너를 노출해야 한다. 이 배너는 사용자가 다른 페이지로 이동하면 자동으로 사라진다 (세션·쿠키에 상태를 저장하지 않음).
- **FR-104**: 시스템은 "승인 대기" 상태 계정에 대해 로그인을 허용해서는 안 된다. 자격 증명이 올바르더라도 세션을 발급하지 않고 승인 대기 안내 메시지를 반환해야 한다.
- **FR-105**: 시스템은 "승인됨" 상태로 바뀐 계정에 대해서는 이후 로그인을 정상 처리해야 한다. 별도의 재가입 절차 없이 원래 자격 증명으로 로그인 가능해야 한다.
- **FR-106**: 시스템은 이미 활성 세션을 가진 사용자의 승인 상태가 "승인 대기"로 되돌아간 경우, 그 사용자의 보호된 화면 접근을 다음 서버 상호작용부터 차단해야 한다.
- **FR-107**: 로그인 시도가 자격 증명 오류와 승인 대기 상태를 동시에 만족할 경우(잘못된 비밀번호 + 미승인 계정), 시스템은 자격 증명 오류 안내를 우선 반환해야 한다 (승인 상태 유출 방지).
- **FR-108**: 시스템은 앱 UI 안에 관리자 전용 화면·관리자 액션·승인 조작 API를 노출해서는 안 된다. 승인 상태 변경은 앱 외부(소유자가 DB 값을 직접 변경) 경로로만 가능해야 한다.
- **FR-109**: 마이그레이션 시점에 이미 존재하던 계정은 "승인됨" 상태로 기본 설정되어야 한다 (기존 사용자의 접근이 예기치 않게 끊기지 않도록).

**UI 전면 재디자인 (US2)**

- **FR-201**: 앱의 모든 화면은 [DESIGN.md](../../DESIGN.md)에서 정의한 색상 토큰(primary mint, neutrals, semantic accents)을 기반으로 렌더되어야 한다. 임시 하드코딩된 색 값이 남아 있어서는 안 된다.
- **FR-202**: 앱의 모든 화면은 [DESIGN.md](../../DESIGN.md)의 타이포그래피 규칙(헤드라인은 디스플레이 폰트, 본문은 Pretendard 등)을 따라야 한다. 헤드라인과 본문의 폰트 계열이 시각적으로 구분되어야 한다.
- **FR-203**: 앱의 모든 화면은 [DESIGN.md](../../DESIGN.md)의 간격·라운드·엘리베이션 토큰을 사용해야 한다. 카드는 라운드된 모서리를 갖고, 주요 액션 버튼은 알약(pill) 형태여야 한다.
- **FR-204**: 앱은 단일 반응형 웹앱으로서 모바일 브라우저(뷰포트 폭 ≤ 640px)와 데스크톱 브라우저(≥ 1024px) 양쪽에서 사용 가능해야 한다.
- **FR-205**: 모바일 뷰포트에서 로그인된 사용자에게는 화면 하단에 탭 바가 노출되어야 하며, 탭은 정확히 3개다: (1) 내 문제집 → `/sets`, (2) 공개 문제집 → `/public-sets`, (3) 프로필 → `/profile`. 각 탭에는 아이콘과 한글 라벨이 함께 표시된다. 현재 활성 탭은 시각적으로 명확히 구분되어야 한다.
- **FR-205a**: 프로필 페이지(`/profile`)는 로그인된 사용자의 아이디를 표시하고 로그아웃 액션 버튼을 제공해야 한다. 다른 계정 관련 기능(예: 비밀번호 변경)은 이 스펙 범위 밖이며, 프로필 페이지는 향후 확장을 위한 자리로만 준비된다.
- **FR-205b**: 학습·암기 모드 화면(`/sets/[id]/study`, `/public-sets/[id]/study`)에서는 모바일 하단 탭 바를 렌더하지 않아야 한다 (학습 몰입 확보). 사용자가 문제집 목록·상세 등 다른 화면으로 이동하면 탭 바가 다시 노출되어야 한다. 그 외의 상세·편집 화면에서는 탭 바가 유지된다.
- **FR-206**: 데스크톱 뷰포트에서 로그인된 사용자에게는 화면 상단에 내비게이션 바가 노출되어야 하고, 하단 탭 바는 노출되지 않아야 한다. 상단 내비게이션 바에는 하단 탭 바와 동일한 3개의 목적지(내 문제집·공개 문제집·프로필)로의 링크가 있어야 하며, 위계를 이해할 수 있게 시각적으로 정리된다.
- **FR-207**: 앱의 어떤 화면·어떤 뷰포트에서도 footer 영역은 렌더되지 않아야 한다 (기존 규칙 유지, spec 001의 FR-025 승계).
- **FR-208**: 입력 폼(로그인·회원가입·문제집·문제)은 [DESIGN.md](../../DESIGN.md)의 `text-field` 사양(높이·radius·서브틀 배경·포커스 시 강한 보더)을 따라야 한다.
- **FR-209**: 키워드 입력 UI의 각 키워드 chip은 [DESIGN.md](../../DESIGN.md)의 tag/chip 어휘(알약 배경 + 텍스트 + ✕ 제거 버튼)로 표시되어야 한다.
- **FR-210**: 학습/암기 모드의 문제 카드는 [DESIGN.md](../../DESIGN.md)의 카드 컴포넌트 토큰(라운드·표면색·그림자 최소화)을 따라야 한다.
- **FR-211**: 인터랙션 애니메이션은 [DESIGN.md](../../DESIGN.md)의 animation 토큰(120~400ms, ease-out, 통통 튀는 spring 없음)을 준수해야 한다.
- **FR-212**: 안전 영역(safe-area): 모바일 하단 탭 바는 홈 인디케이터·노치 등 시스템 UI와 겹치지 않도록 safe-area 여백을 확보해야 한다.
- **FR-213**: 디스플레이 폰트 로딩 실패 시 시스템 sans-serif로 fallback되어 텍스트가 항상 읽을 수 있어야 한다.
- **FR-214**: 이 스펙 범위에서 다크 모드는 지원하지 않는다 (라이트 모드만).

### Key Entities

- **User (사용자)** — 기존 개념 유지, 다음 속성 추가:
  - **승인 상태**: 계정이 앱을 실제로 사용할 수 있는지를 나타내는 명시적 값. 회원가입 직후 기본값은 "승인 대기". 소유자가 앱 밖에서 이 값을 "승인됨"으로 변경해야 로그인이 가능해진다.
  - **승인된 시점 (선택)**: 감사 목적으로 언제 승인되었는지 기록될 수 있다 (구현 재량, 스펙이 강제하지 않음).

- **디자인 토큰 (Design Token)** — [DESIGN.md](../../DESIGN.md)에 정의된 색상·타이포·간격·라운드·엘리베이션·애니메이션 값의 집합. 앱은 이 값들을 직접 참조하며, 컴포넌트별로 하드코딩된 값을 두지 않는다.

- **뷰포트 프로파일 (Viewport Profile)** — 두 가지: **모바일**(≤ 640px)과 **데스크톱**(≥ 1024px). 640~1024px 사이는 두 프로파일 중 하나로 자연스럽게 전이(태블릿 별도 프로파일 없음).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 승인되지 않은 사용자가 로그인·보호된 데이터 조회에 성공한 사례가 0건이다.
- **SC-102**: 회원가입 후 승인까지의 흐름(가입 폼 제출 → 안내 화면 확인 → 소유자가 DB에서 승인 → 재로그인 성공)이 사용자·소유자 합쳐 5단계 이내로 완결된다.
- **SC-103**: 앱의 모든 페이지가 모바일(375×667)과 데스크톱(1440×900) 두 뷰포트에서 콘텐츠 겹침·가로 스크롤 없이 렌더된다.
- **SC-104**: 모든 페이지의 색상·주요 버튼·입력 필드가 시각적으로 [DESIGN.md](../../DESIGN.md)의 대응 컴포넌트와 일관되게 인식된다 (직접 비교 검수 기준으로 색 편차 ≤ 5%, 라운드/간격은 토큰 값과 일치).
- **SC-105**: 모바일 뷰포트에서 하단 탭 바 노출 페이지 비율 = 100% (로그인 후 접근하는 모든 페이지 중, 학습·암기 모드 두 경로를 제외한 나머지 전부).
- **SC-106**: 어느 뷰포트·어느 페이지에서도 footer 영역이 렌더되는 사례가 0건이다.
- **SC-107**: 사용자가 학습 모드의 "다음" 액션을 취했을 때 새 문제가 나타나기까지 걸리는 지각 시간은 이전 스펙과 동일한 1초 이내를 유지한다 (재디자인으로 인한 성능 퇴보 없음).
- **SC-108**: 첫 방문 시 필수 폰트·CSS·JS의 총 다운로드 용량이 500KB(gzip 기준)를 넘지 않는다 (모바일 3G 환경에서도 실용적 로딩 시간 확보).

## Assumptions

- **관리자 UI는 이 스펙 범위 밖**이다. 소유자가 Supabase 대시보드나 SQL로 직접 승인 상태를 변경한다는 것을 전제로 한다 (사용자 명시).
- **다중 관리자 개념은 없다.** 이 스펙에서는 "일반 사용자" 하나의 역할만 존재하며, 승인/미승인은 그 역할 내의 상태 구분이다.
- **승인/거절 이력은 저장하지 않는다.** 현재 상태만 기록하는 최소 필드로 시작한다 (필요 시 후속 스펙에서 감사 로그 확장).
- **DESIGN.md의 배민 디자인 시스템**은 오픈 폰트(SIL OFL)와 공개 브랜드 자료를 재구성한 자료이며, 상업적 사용에 라이선스 걸림돌이 없다. 실제 배민 앱과의 미묘한 편차는 감수한다.
- **네이티브 앱은 이 스펙 범위 밖**이다. "웹/앱"은 "웹 브라우저의 모바일/데스크톱 양쪽"을 뜻하며, iOS/Android 네이티브 애플리케이션 개발은 포함하지 않는다.
- **반응형 브레이크포인트**는 모바일(≤ 640px)과 데스크톱(≥ 1024px) 두 축을 기본으로 하고, 그 사이 구간은 두 프로파일 중 하나로 자연스럽게 전이한다. 태블릿 전용 레이아웃은 스펙 범위 밖.
- **다크 모드·i18n·접근성 세부**(스크린리더 최적화 등)는 이 스펙 범위 밖. 색 대비는 WCAG AA 최소 준수를 목표로 하되 별도 인증 검사는 하지 않는다.
- **기존 승인 없이 로그인 가능한 계정**은 이 스펙의 마이그레이션 단계에서 모두 "승인됨" 상태로 시작하는 것으로 가정한다 (개발 중 만들어 둔 테스트 계정도 포함).
- **캐릭터·마스코트 자산**(배달이 캐릭터 등)은 라이선스 문제로 사용하지 않으며, DESIGN.md에서도 image-slot placeholder로 처리된다. 이 앱도 동일하게 처리하거나 자체 대체 일러스트/이모지로 대신한다.
- **DESIGN.md의 컴포넌트 목록 전부를 구현할 필요는 없다.** 이 스펙 범위에서 실제 UI에 필요한 컴포넌트(text-field, button-primary/mint/ghost, tag/chip, card, list-row, bottom-tab-bar 등)만 채택하고, 나머지(coupon-banner 등)는 향후 필요 시 추가한다.
