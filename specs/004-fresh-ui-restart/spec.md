# Feature Specification: UI 처음부터 재구축 — 모던 감각 + 자연스러운 모바일 모션

**Feature Branch**: `004-fresh-ui-restart`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "현재 UI(003 Linear 톤 기반)가 취향에 안 맞음. 처음부터 다시 만들되 (1) 더 모던하고 감각적인 UI/UX를 원함, (2) 모바일에서 화면 이동 모션이 전혀 자연스럽지 않음. 003의 시각·모션 결정은 초기화 대상, 002의 인증/데이터 규칙은 유지."

## Clarifications

### Session 2026-08-23

- Q: 시각·모션의 앵커가 될 긍정 레퍼런스 앱은? → A: **Toss · Naver Webtoon · 텔레그램**. 공통점: 모바일-우선 앱 감각, 파란 계열 액센트(Toss #3182F6 · Telegram #0088CC · Webtoon 라임·블루 혼용), 청키·둥근 컨테이너(카드/말풍선/썸네일), 스냅·스프링 자연스러운 모션, 크롬 최소화·콘텐츠 우선. Planning은 이 세 앱의 공통 결을 앵커로 삼는다.
- Q: 테마 모드는 라이트/다크/자동 중 어느 것을 채택하는가? → A: **다크 온리**. 딥 뉴트럴 캔버스 + 파란 계열 액센트. 학습 몰입 · 눈 피로도 · 세 레퍼런스 앱과의 정합성 우선. 라이트 모드와 `prefers-color-scheme` 자동 스위칭은 이 스펙 범위 밖.
- Q: 모바일 라우트 전환 모션의 성격은? → A: **iOS-스타일 좌우 슬라이드 + 스프링 이징**. 앞으로(더 깊은 경로) = 새 화면이 오른쪽에서 밀려들어오고 이전 화면은 왼쪽으로 살짝 밀리며 parallax; 뒤로 = 반대. 이징은 스프링 감쇠(damping 있는 자연 감쇠, 예: `cubic-bezier(0.32, 0.72, 0, 1)` 또는 spring 라이브러리). 데스크톱은 방향성 없는 절제된 fade 유지.

## Overview

003의 시각·모션 결정을 전면 폐기하고 UI를 처음부터 재설계한다. 002의 인증·승인·데이터·RLS는 그대로 유지되므로 이 스펙은 **표면(surface) + 모션 계층 재작성**이다. 003과 달리 이번은 특정 참조 시스템(Linear·Airtable·Discord 등)을 앵커로 고정하지 않는다 — 사용자가 "reject-cycle"에서 나올 수 있도록 clarify 단계에서 **긍정 레퍼런스 앱**을 먼저 잡는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 모던하고 감각적인 시각 언어 (Priority: P1)

사용자가 앱 어느 화면을 열든 "이 앱은 잘 디자인되었다"는 첫인상을 받는다. 색·타이포·간격·라운드·엘리베이션이 하나의 일관된 톤으로 짜여 있어 튀는 요소가 없고, 그러면서도 무미건조하지 않다. 화면마다 눈이 가야 할 곳이 명확하고 위계가 시각적으로 뚜렷하다.

**Why this priority**: 사용자가 명시적으로 "취향에 안 맞음 → 다시 만들자"라고 요청한 지점. 이 첫인상이 잡히지 않으면 이후 어떤 기능을 얹어도 재리디자인 사이클이 반복된다.

**Independent Test**: 로그인 후 4개 대표 화면(내 문제집 목록·문제집 상세·학습 모드·프로필)을 순회하면서, 사용자가 "모던하다·감각적이다"는 주관적 평가에 명시적으로 동의하는지 확인. 실무 판정 기준: (a) 색·라운드·간격이 화면 전반에서 일관되고, (b) 어떤 화면에서도 튀거나 촌스러운 요소를 지목할 수 없고, (c) 사용자가 스스로 "괜찮다"고 말하는지.

**Acceptance Scenarios**:

1. **Given** 어떤 화면에서든, **When** 시각 요소를 스캔하면, **Then** 색·타이포·라운드·간격이 단일 디자인 언어 안에서 일관되게 표현되어 튀는 컴포넌트가 없다.
2. **Given** 카드·리스트·폼·버튼 어느 컴포넌트든, **When** 정지 상태를 관찰하면, **Then** 각 요소의 위계(주·보조·비활성)가 즉시 눈에 들어온다.
3. **Given** 사용자가 앱을 처음 열어본 사람이라면, **When** 3분 이내로 훑고 소감을 요청하면, **Then** "모던하다" 또는 유사한 긍정 형용사를 스스로 언급한다 (부정 형용사만 나오면 실패).
4. **Given** 데스크톱과 모바일 뷰포트를 각각 볼 때, **When** 시각 언어를 비교하면, **Then** 두 뷰포트가 동일한 톤으로 일관되게 인식된다 (한쪽이 다른 쪽보다 급이 낮다는 인상이 없어야 함).

### User Story 2 - 자연스러운 모바일 네비게이션 모션 (Priority: P1)

모바일에서 화면 간을 이동하거나 사이드바 drawer를 여닫을 때 "웹페이지"가 아닌 "앱"을 다루는 감각을 준다. 페이지 전환은 방향성을 갖고(더 깊은 경로로 갈 땐 앞으로, 상위로 갈 땐 뒤로), 드로어는 관성 있게 밀리고, 뒤로 가기 제스처가 자연스럽게 동작한다. 현재의 단순 fade+slide 200ms는 "웹 애니메이션"으로 느껴져 부자연스럽다.

**Why this priority**: 사용자가 명시적으로 "모바일 모션이 전혀 자연스럽지 않다"고 지적. 시각(US1)이 갖춰져도 이 감각이 어색하면 여전히 웹앱 느낌이 남아 계속 불만이 남는다.

**Independent Test**: 모바일 뷰포트(375×667)에서 로그인 → 문제집 목록 → 문제집 상세 → 학습 모드 시작 → 두 번 다음 → 목록으로 나가기 순서로 진행하며, (a) 각 라우팅 전환이 방향성 있게 자연스럽고, (b) 사이드바 드로어가 관성 있게 밀리며, (c) 사용자가 "이건 앱 같다"라고 자발적으로 말하는지 확인.

**Acceptance Scenarios**:

1. **Given** 모바일 사용자가 목록에서 상세로 진입할 때, **When** 라우팅이 발생하면, **Then** 새 화면이 방향성 있는 슬라이드(예: 오른쪽에서 들어옴) 또는 유사한 앱 관습적 모션으로 들어온다.
2. **Given** 상세 화면에서 뒤로 갈 때, **When** 뒤로 가기 액션을 취하면, **Then** 진입 때의 방향과 반대로 화면이 빠져나간다 (앞으로 진입 = 오른쪽 슬라이드인 → 뒤로 = 오른쪽 슬라이드아웃).
3. **Given** 모바일 드로어를 열 때, **When** 햄버거 버튼을 탭하면, **Then** 드로어가 관성 있게 부드럽게 밀려나오고, 백드롭 페이드가 자연스럽게 동반된다 (딱딱한 슬라이드 아님).
4. **Given** 학습 모드에서 카드를 다음/이전으로 넘길 때, **When** 액션을 취하면, **Then** 카드가 앱 관습에 부합하는 모션으로 전환된다 (fade-only가 아닌, 방향성 또는 spring 느낌 포함).
5. **Given** `prefers-reduced-motion: reduce`가 설정된 사용자에게는, **When** 어떤 모션이든 트리거되면, **Then** 모든 방향성 애니메이션이 즉시 전환으로 대체된다 (접근성 유지).

---

### Edge Cases

- **모바일 드로어 스와이프**: 사용자가 왼쪽에서 오른쪽으로 스와이프해 드로어를 열거나, 열린 드로어를 왼쪽 스와이프로 닫는 것이 가능한지는 clarify에서 결정.
- **저성능 기기**: 방향성 슬라이드 모션이 60fps를 유지하지 못하면 최소한 fade로 폴백해야 하며, 프레임 드롭이 시각적으로 튀지 않아야 함.
- **매우 넓은 데스크톱 (2K/4K)**: 콘텐츠 폭이 지나치게 길게 흐르지 않도록 max-width 유지. 좌우 여백은 배경으로 자연스럽게 흡수.
- **매우 좁은 모바일 (320px)**: 사이드바 드로어가 화면 폭 대부분을 차지해도 백드롭 일부는 탭 가능해야 함.
- **iOS Safari 뒤로 가기 제스처**: 스와이프 뒤로 가기 시 페이지 전환 애니메이션과 충돌해 이중 이동감이 없어야 함.
- **PWA/홈 화면 저장 시**: 앱 아이콘·splash 대응(포함 여부는 이 스펙 범위 밖, 다만 방해되지 않도록).

## Requirements *(mandatory)*

### Functional Requirements

**시각 시스템 (US1)**

- **FR-401**: 003 스펙에서 도입한 Linear 톤의 시각 결정(얇은 회색 보더 위주 위계, 서브틀한 mint 액센트 바, near-white 캔버스 등)은 이 스펙 배포 이후 앱에서 렌더되지 않아야 한다.
- **FR-402**: 앱 전 화면이 단일 디자인 언어(색·타이포·간격·라운드·엘리베이션의 정합된 집합) 안에서 표현되어야 하며, 화면 간 시각적 결의 급차가 없어야 한다.
- **FR-403**: 브랜드 강조 색은 정확히 한 종류(주 액센트), 필요 시 최대 두 종류(주 액센트 + 하이인텐트 CTA)까지만 사용된다. 그 외 색은 회색/뉴트럴 스케일 안에서만 표현.
- **FR-404**: 카드·컨테이너·버튼·인풋 등 재사용 컴포넌트는 일관된 라운드 스케일 계층(예: input · button · card 각 단계)을 따른다.
- **FR-405**: 헤드라인·본문·캡션의 타이포 위계가 시각적으로 뚜렷하되, 헤드라인이 지나치게 heavy하거나 지나치게 light하지 않고 감각적으로 균형 잡혀야 한다.
- **FR-406**: 어떤 뷰포트에서도 콘텐츠가 지나치게 길게 흐르지 않도록 max-width 상한이 있어야 한다.
- **FR-407**: 이 스펙 범위에서 footer는 계속 렌더되지 않는다 (기존 규칙 승계).

**모션 시스템 (US2)**

- **FR-408**: 모바일 뷰포트의 라우트 전환은 **iOS-스타일 좌우 슬라이드 + 스프링 이징**을 사용해야 한다. 앞으로(더 깊은 경로) 진입 시 새 화면이 오른쪽에서 슬라이드인 하고 이전 화면은 왼쪽으로 살짝(약 20~30% 이동) 밀리는 parallax 효과를 갖는다. 뒤로 이동 시에는 방향이 반대다. 이징은 스프링 감쇠(damping 있는 자연 감쇠). fade-only는 사용하지 않는다.
- **FR-409**: 모바일 사이드바 drawer는 관성감 있는 부드러운 전환으로 열리고 닫히며, 백드롭 페이드가 동반된다. 딱딱한 즉시 슬라이드는 부자연스러운 것으로 판정된다.
- **FR-410**: 데스크톱 뷰포트의 라우트 전환은 방향성 슬라이드 없이 절제된 fade 또는 fade+minor slide로 처리한다 (마우스 사용자에게 방향성 모션은 오히려 산만함).
- **FR-411**: 학습·암기 모드의 카드 전환은 즉시 컷아웃이 아니어야 하며, 모바일에서는 방향성(다음=왼쪽으로 나감, 이전=오른쪽으로 나감) 또는 그에 준하는 앱 관습을 따른다.
- **FR-412**: 모든 인터랙션 요소(버튼·링크·카드·사이드바 항목)는 hover/active 시 미묘한 피드백을 준다.
- **FR-413**: `prefers-reduced-motion: reduce`가 설정된 사용자에게는 방향성 슬라이드·spring·관성 모션이 즉시 전환으로 대체된다.

**모바일 특화 (US1 + US2)**

- **FR-414**: 모든 인터랙티브 요소의 터치 영역은 최소 44×44 CSS 픽셀 이상이어야 한다.
- **FR-415**: 모바일에서 인풋 포커스 시 자동 확대되지 않아야 한다 (iOS Safari 대응).
- **FR-416**: 안전 영역(safe-area) 여백을 확보해 노치·홈 인디케이터와 겹치지 않는다.
- **FR-417**: iOS Safari의 스와이프 뒤로 가기 제스처와 앱의 라우트 전환 애니메이션이 충돌하지 않아야 한다 (이중 이동감 없음).

**범위**

- **FR-418**: 002 스펙의 승인제·인증·데이터 접근·RLS 규칙은 이 스펙에서 변경되지 않는다.
- **FR-419**: 003 스펙의 좌측 접이식 사이드바 아키텍처는 유지된다. 다만 그 안의 시각·모션은 이 스펙에서 재정의된다.

### Key Entities

- **디자인 토큰(Design Token)** — 색·타이포·간격·라운드·엘리베이션·모션 값의 집합. 이 스펙에서 완전히 재정의된다.
- **모션 프로파일(Motion Profile)** — 데스크톱 vs 모바일의 전환 지속 시간·이징·방향성 규칙.
- **뷰포트 프로파일(Viewport Profile)** — 모바일(≤ 640px)과 데스크톱(≥ 641px). 002 정의 승계.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-401**: 사용자가 앱을 처음 열고 3분 이내에 "모던하다·감각적이다·괜찮다" 계열의 긍정 형용사를 스스로 발화한다 (부정 형용사만 발화 시 실패).
- **SC-402**: 화면 전 요소 중 사용자가 "촌스럽다·튄다·안 어울린다" 계열로 지목하는 요소가 0개다.
- **SC-403**: 모바일 뷰포트에서 라우트 전환 시 방향성 있는 모션이 관찰된다 (스크린 녹화 기준, 진입 방향과 이탈 방향이 시각적으로 대응).
- **SC-404**: 사용자가 모바일에서 사이드바 드로어를 열고 닫는 것을 "자연스럽다·부드럽다"고 평가한다.
- **SC-405**: 모든 모바일 인터랙션 요소가 44×44 CSS 픽셀 이상의 터치 영역을 갖는다 (100%).
- **SC-406**: `prefers-reduced-motion: reduce` 사용자에게 방향성 애니메이션이 100% 즉시 전환으로 대체된다.
- **SC-407**: 초기 로드 필수 자산(gzip) ≤ 500KB (SC-309 승계).
- **SC-408**: 라우트 전환 시 콘텐츠 레이아웃 시프트 CLS ≤ 0.05.

## Assumptions

- **네이티브 앱은 이 스펙 범위 밖.** 반응형 웹앱이 모바일 브라우저에서 앱 감각을 주는 것이 목표.
- **좌측 접이식 사이드바 아키텍처 유지** (003 결정 승계). 이 스펙은 사이드바의 시각·모션을 재정의하지만 구조는 그대로.
- **002의 승인제·인증·RLS 규칙 유지.** 이 스펙에서 손대지 않음.
